# 需求文档

## 简介

家庭菜谱 App v2 迭代，在已完成的 MVP 基础上增强功能体验。主要包括：自定义应用图标、菜谱封面图片支持、增强搜索（按家庭成员偏好筛选）、菜谱分类枚举化、随机选菜功能、多维排序与收藏/置顶、推荐指数评分，以及架构工程化改进（Hilt DI、Room schema 导出、单元测试与 UI 测试）。

## 术语表

- **App**: 家庭菜谱 Android 应用程序
- **Recipe**: 菜谱实体，包含名称、描述、步骤、烹饪时间、难度、分类、封面图片等字段
- **FamilyMember**: 家庭成员实体，包含姓名、代表色、备注
- **RecipePreference**: 家庭成员对菜谱的偏好记录（喜欢/中立/不喜欢）
- **RecipeCategory**: 菜谱分类枚举，包含炒菜、煲汤、速食等预定义类型
- **RecommendationIndex**: 菜谱推荐指数，1-5 星评分
- **ImagePicker**: 图片选择器组件，支持从相册或相机获取图片
- **RandomSelector**: 随机选菜功能模块
- **SortDimension**: 排序维度，包括时间、难度、推荐指数等
- **SettingsStore**: 应用设置持久化存储（DataStore）
- **Hilt**: Dagger Hilt 依赖注入框架
- **Room Schema**: Room 数据库 schema 导出配置，用于支持数据库迁移

## 需求列表

### 需求 1：应用图标

**用户故事：** 作为用户，我希望应用有一个独特且易于辨认的图标，以便在设备上快速找到它。

#### 验收标准

1. 应用应显示一个包含至少一个可识别的烹饪相关视觉元素（如菜谱书、餐具或食物）的自定义启动器图标，与默认 Android 占位图标明显区分
2. 应用应在 mipmap-anydpi-v26 资源目录中提供自适应图标定义（前景层 + 背景层），并在 mdpi（48×48px）、hdpi（72×72px）、xhdpi（96×96px）、xxhdpi（144×144px）和 xxxhdpi（192×192px）密度桶中提供传统 PNG 图标
3. 应用应通过 AndroidManifest 中的 android:roundIcon 属性引用圆形图标变体（ic_launcher_round），使用自适应图标格式
4. 当应用安装在 Android API 26（minSdk）到 API 34（targetSdk）的设备上时，启动器图标应在设备原生显示密度下无裁剪或变形地渲染

---

### 需求 2：菜谱封面图片

**用户故事：** 作为用户，我希望为菜谱添加封面图片，以便通过视觉快速识别菜品，让菜谱列表更有吸引力。

#### 验收标准

1. 当用户创建或编辑菜谱时，编辑页面应显示一个图片选择区域，未设置图片时显示占位图标，已有图片时显示当前封面
2. 当用户点击图片选择区域时，应提供从设备相册选择图片或使用相机拍摄新照片的选项
3. 当用户选择或拍摄图片后，应用应将图片缩放至最长边不超过 1920px，复制到应用内部存储，并将文件路径存储到 Recipe 的 coverImagePath 字段
4. 当菜谱设置了封面图片时，菜谱列表页应在卡片中显示封面缩略图（缩放适配卡片高度）
5. 当菜谱设置了封面图片时，菜谱详情页应在顶部以全屏宽度显示封面图片
6. 当用户点击已有封面图片的选择区域时，应允许替换当前图片，并删除之前存储的旧图片文件
7. 当用户移除封面图片时，应用应删除内部存储中的图片文件并将 coverImagePath 设为 null
8. 如果引用的图片文件缺失或无法解码，应用应显示占位图片且不崩溃
9. 如果用户拒绝相机或存储权限，应用应显示提示信息说明需要该权限，并返回编辑页面不做任何更改

---

### 需求 3：按家庭成员偏好增强搜索

**用户故事：** 作为用户，我希望能按家庭成员的口味偏好搜索菜谱，以便快速找到特定成员喜欢的菜或全家都爱的菜。

#### 验收标准

1. 当用户打开搜索界面时，菜谱列表页应在文本搜索框下方显示一行可水平滚动的家庭成员筛选标签（显示成员姓名）
2. 当用户选择一个成员筛选标签时，应用应仅显示该成员明确标记为"喜欢"的菜谱
3. 当用户选择多个成员筛选标签时，应用应仅显示所有选中成员都明确标记为"喜欢"的菜谱
4. 当用户点击已选中的筛选标签时，应取消选中并从活跃筛选条件中移除该成员
5. 当用户激活"全家都爱"筛选时，应用应仅显示系统中所有已注册家庭成员都对该菜谱有明确"喜欢"记录的菜谱
6. 当文本搜索和成员偏好筛选同时激活时，应用应同时应用两个筛选条件（取交集）
7. 当没有菜谱匹配组合筛选条件时，应用应显示空状态提示，说明没有匹配的菜谱并建议调整筛选条件
8. 如果某菜谱对选中的家庭成员没有偏好记录，应用应将该菜谱从筛选结果中排除

---

### 需求 4：菜谱分类枚举

**用户故事：** 作为用户，我希望从预定义列表中选择菜谱分类，以便分类一致且可以按类型筛选菜谱。

#### 验收标准

1. RecipeCategory 枚举应定义以下值：STIR_FRY（炒菜）、SOUP（煲汤）、QUICK_MEAL（速食）、STAPLE（主食）、COLD_DISH（凉菜）、DESSERT（甜品）、BEVERAGE（饮品）、OTHER（其他）
2. 当用户创建或编辑菜谱时，编辑页面应提供下拉或标签选择器，从 RecipeCategory 枚举中选择恰好一个分类；新建菜谱时无预选，编辑时预选已有分类
3. 当数据库迁移执行时，应用应使用精确或子串匹配中文标签（炒菜、煲汤、速食、主食、凉菜、甜品、饮品）将现有自由文本分类值映射到 RecipeCategory 枚举值
4. 如果迁移时现有分类值不匹配任何中文标签，应用应分配 OTHER 分类
5. 当用户查看菜谱列表时，应显示每个菜谱的本地化分类名称（中文标签）
6. 当用户按分类筛选时，应用应仅显示匹配所选单个 RecipeCategory 值的菜谱
7. 当用户未选择任何分类筛选时，菜谱列表应显示所有菜谱
8. 当用户创建或编辑菜谱时，编辑页面应要求选择分类后才能保存，并标明分类字段为必填

---

### 需求 5：随机选菜

**用户故事：** 作为用户，我希望有一个"今天吃什么"随机选菜功能，以便在不知道做什么菜时获得灵感。

#### 验收标准

1. 当用户激活随机选菜功能时，随机选择器应使用均匀随机分布从完整菜谱列表中随机选择菜谱
2. 当用户未指定自定义数量时，随机选择器应选择等于用户配置的默认数量的菜谱
3. 当用户触发随机选择时，应允许指定 1 到 10 之间的自定义数量，覆盖该次选择的默认值
4. 如果菜谱总数少于请求数量，随机选择器应选择所有可用菜谱并显示提示说明可用菜谱少于请求数量
5. 随机选择器应确保单次随机选择结果中不出现重复菜谱
6. 当用户点击"换一批"操作时，随机选择器应以与当前结果相同的数量生成新的随机选择
7. 设置存储应持久化默认随机选择数量，初始值为 3，有效范围为 1 到 10
8. 如果随机选择激活时菜谱列表为空，随机选择器应显示提示说明没有可用菜谱且不执行选择

---

### 需求 6：多维排序与收藏置顶

**用户故事：** 作为用户，我希望按不同维度排序菜谱并将收藏置顶，以便高效组织和快速访问常用菜谱。

#### 验收标准

1. 菜谱列表页应支持按以下维度排序：更新时间、创建时间、烹饪时间、难度和推荐指数，初始加载时默认按更新时间排序
2. 当用户选择一个排序维度时，菜谱列表应按所选维度默认降序排列（时间和数值维度为最新/最高值优先）
3. 当用户再次点击当前激活的排序维度时，菜谱列表应在升序和降序之间切换
4. 当用户将菜谱标记为收藏时，应用应将收藏状态持久化到 Recipe 实体中
5. 当菜谱列表显示时，收藏的菜谱应始终显示在列表顶部，不受当前排序维度影响；收藏菜谱之间按当前激活的排序维度和顺序排列
6. 当用户切换菜谱的收藏状态时，菜谱列表应立即更新排序，无需手动刷新或导航
7. 菜谱详情页应显示收藏切换按钮，允许标记或取消标记菜谱为收藏
8. 当搜索或分类筛选激活时，菜谱列表应对筛选后的结果集应用所选排序维度和收藏置顶规则

---

### 需求 7：推荐指数

**用户故事：** 作为用户，我希望为菜谱评定推荐指数，以便追踪哪些菜谱最值得再做。

#### 验收标准

1. Recipe 实体应包含 recommendationIndex 字段，整数值范围 1 到 5，默认值为 3
2. 当用户创建或编辑菜谱时，编辑页面应显示一行 5 个可点击的星形图标，点击第 N 个星设置推荐指数为 N，第 1 到第 N 个星显示为实心，第 N+1 到第 5 个星显示为空心
3. 当用户在列表中查看菜谱时，菜谱列表页应以 5 个星形图标显示推荐指数，实心星代表评分值，空心星代表剩余部分
4. 当用户查看菜谱详情时，详情页应在描述上方的头部区域以 5 个星形图标显示推荐指数
5. 应用应将推荐指数作为菜谱列表中可用的排序维度
6. 如果用户保存菜谱时未与星形选择器交互，应用应持久化默认推荐指数值 3

---

### 需求 8：Hilt 依赖注入迁移

**用户故事：** 作为开发者，我希望从手动 DI（AppContainer）迁移到 Hilt，以便依赖管理标准化、可测试且可扩展。

#### 验收标准

1. 应用应为 RecipeApplication 添加 @HiltAndroidApp 注解，为所有 Activity 类添加 @AndroidEntryPoint 注解
2. 应用应定义 Hilt 模块，以 Singleton 作用域提供 AppDatabase 实例，并从该数据库实例提供 RecipeDao、FamilyMemberDao 和 RecipePreferenceDao
3. 应用应通过 Hilt 使用 @Inject 构造函数注入或显式模块 @Provides 方法提供 RecipeRepository 和 FamilyMemberRepository，作用域为 Singleton
4. 应用应为所有 ViewModel 类添加 @HiltViewModel 注解，通过 @Inject 构造函数注入其 Repository 依赖，移除所有 ViewModelProvider.Factory 伴生类
5. Hilt 迁移完成后，应用应不包含对 AppContainer 类的引用、不包含手动 ViewModelProvider.Factory 实现、不在 Hilt 模块外直接实例化 Repository 或 DAO
6. 应用应在 Hilt 注解处理下成功编译，并保持与迁移前相同的用户界面导航流程、数据持久化和页面渲染行为

---

### 需求 9：Room Schema 导出与迁移支持

**用户故事：** 作为开发者，我希望 Room 导出数据库 schema，以便为数据库变更创建正确的迁移路径，避免应用更新时数据丢失。

#### 验收标准

1. AppDatabase 应将 exportSchema 设为 true，并在构建配置中配置 schema 导出目录
2. 当数据库 schema 变更（添加 recommendationIndex、isFavorite、分类枚举）时，应用应提供从版本 1 到版本 2 的 Room Migration，保留 recipes 表中所有现有行数据
3. Migration 应添加 recommendationIndex 列，类型为 NOT NULL INTEGER，默认值为 3
4. Migration 应添加 isFavorite 列，类型为 NOT NULL INTEGER，默认值为 0（代表 false）
5. Migration 应使用大小写不敏感匹配，将现有自由文本 category 列值转换为对应的 RecipeCategory 枚举字符串值（如"炒菜"映射为"STIR_FRY"，"煲汤"映射为"SOUP"）
6. 如果迁移时 category 值不匹配任何预定义的 RecipeCategory 枚举名称或中文标签，Migration 应将 category 设为"OTHER"
7. 如果迁移在任何环节失败，应用应不损坏现有数据库，并通过 Room 的标准回退机制报告迁移错误

---

### 需求 10：单元测试与 UI 测试

**用户故事：** 作为开发者，我希望有覆盖核心业务逻辑和关键 UI 流程的自动化测试，以便在重构和添加功能时有信心。

#### 验收标准

1. 项目应包含单元测试依赖（JUnit、MockK、Coroutines Test、Room Testing）
2. 项目应包含 UI 测试依赖（Compose UI Test、Espresso）
3. 项目应包含 RecipeRepository 的单元测试，覆盖插入、按 ID 查询、更新、删除操作和偏好查询（getPreferencesForRecipe、getRecipeIdsByMemberPreference、setPreference、removePreference），每个操作至少一个测试用例验证预期返回值或状态变更
4. 项目应包含随机选择算法的单元测试，验证单次结果中不出现重复菜谱、当有足够菜谱时结果数量等于请求数量、在 1000 次重复选择中从 5 个或更少菜谱的池中每个菜谱至少被选中一次
5. 项目应包含数据库迁移的单元测试，验证 recommendationIndex 列默认为 3、isFavorite 列默认为 false、现有分类文本值映射到正确的 RecipeCategory 枚举字符串、不匹配的分类值映射为"OTHER"
6. 项目应包含菜谱创建流程的 UI 测试，验证名称字段、描述字段、分类选择器和烹饪时间字段可以填写，点击保存操作后菜谱被持久化并导航回菜谱列表
7. 项目应包含搜索和筛选流程的 UI 测试，验证选择家庭成员筛选标签后仅显示该成员标记为"喜欢"的菜谱，以及文本搜索与成员筛选组合后仅显示同时匹配两个条件的菜谱
